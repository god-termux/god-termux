# Сборка god-termux в GitHub Actions

Заметки от 2026-11-24: как собрать полноценный APK форка в CI, что для этого пришлось исправить, что проверено и что нет.

## Итог

Workflow `Build` (`.github/workflows/debug_build.yml`) собирает APK, в котором есть всё, что обычно кладёт `god/build-local.sh` на телефоне: glibc-шим, `fhs-run`, `libdapt-nolink.so`, все скрипты рантайма, Wayland-композитор (`libwlcomp.so` с зависимостями) и glibc-библиотеки `god-lib`. Раньше CI собирал обычный Termux-вариант без этих частей, и такой APK ломал glibc-процессы после установки.

Запуск: push в `god-termux`, `master`, `github-releases/**` или PR в `master`. Два варианта сборки: `apt-android-7` и `apt-android-5` (для телефона нужен `apt-android-7`, архив `..._arm64-v8a`).

## Что было не так в CI-сборке

Первый APK из CI (`c00a330`) собрался без ошибок, но в `assets/god` не было:

- `libfhs-glibc.so` (шим для всех glibc-процессов: Claude Desktop, Chrome, XFCE);
- `libdapt-nolink.so`;
- скриптов `dsu`, `dsu-tx-server.py`, `xfce-wl`, `claude-chrome-host`, `wlbench`, `wlchromium`, `xfce-status` (были только `dapt`, `gsh`, `wlrun`);
- `libwlcomp.so` (в `Android.mk` композитора нет, его собирал только `build-local.sh`);
- `god-lib` (`libSPIRV-Tools.so`, `libwayland-client` 1.26).

`GodRuntime` при старте разворачивает именно содержимое APK, поэтому установка такого файла оставила бы телефон без glibc-шима. Установку тогда остановили.

## Что изменено

| Файл | Изменение |
|---|---|
| `app/build.gradle`, задача `generateGodAssets` | Копирует все скрипты рантайма; собирает `libdapt-nolink.so` для каждого ABI; для arm64 собирает `libfhs-glibc.so` через `aarch64-linux-gnu-gcc` (если он есть в `PATH`); в `SHA256SUMS` попадают все четыре файла шима. |
| `god/tools/ci/build-native.sh` (новый) | Скачивает из репозитория Termux пакеты `libwayland`, `libffi`, `libandroid-support`; собирает `libwlcomp.so` NDK-clang'ом теми же командами, что `build-local.sh`; кладёт рядом `libwayland-server.so`, `libffi.so`, `libandroid-support.so`, `libc++_shared.so`; собирает `god-lib` через `god/tools/gpu/build-glibc-libs.sh` (неудача даёт предупреждение, а не ошибку). Проверяет, что каждая `NEEDED`-запись `libwlcomp.so` либо системная, либо лежит рядом. |
| `.github/workflows/debug_build.yml` | Триггер на ветку `god-termux`; установка `gcc-aarch64-linux-gnu`, `g++-aarch64-linux-gnu`, `cmake`, `ninja-build`; кэш `god-lib`; шаг `build-native.sh`; шаг проверки состава arm64-APK. |

Шаг «Verify god runtime inside the arm64-v8a APK» роняет сборку, если в APK нет любого из обязательных файлов (шим, скрипты, `libwlcomp.so`, его зависимости, `libc++_shared.so`). `libSPIRV-Tools.so` проверяется как необязательный (предупреждение).

## Слияние `origin/main` (2026-11-24)

В `god-termux` слита ветка `origin/main` (13 коммитов: раздельный экран, переносимость шима на 32-битные и не-arm64 архитектуры, Gradle-правки). Единственный конфликт был в `god/fhs/fhs-run.c`: обе стороны добавили блоки `#define` в одно место, оставлены оба (`SECCOMP_*` и `FHS_AUDIT_ARCH`). Резервная ветка до слияния: `backup/god-termux-pre-merge-20261124`.

Не слиты три ветки dependabot (обновление версий Actions): на локальную сборку они не влияют.

## Ошибка, найденная после установки

Первая «полная» сборка (`9eb0892`) прошла и проверку состава, но композитор на телефоне не работал. Причина: `libwlcomp.so`, собранный NDK-clang'ом, имеет `NEEDED libc++_shared.so`, а в APK этой библиотеки не было (`build-local.sh` копирует её из `$PREFIX/lib`, скрипт для CI — нет). Без неё система не может загрузить `libwlcomp.so`. Проверка состава этого не ловила, потому что `libc++_shared.so` в ней не значилась.

Исправление (коммит `5924efcd`): копирование `libc++_shared.so` из NDK, проверка `NEEDED`-записей в `build-native.sh`, добавление файла в обязательные для шага проверки APK. Сборка `5924efcd` прошла в CI (оба варианта, включая новую проверку состава APK). На телефон этот APK ещё не ставился.

Урок: при сборке с другим компилятором сравнивать не только список файлов, но и `readelf -d` у собранных библиотек.

## Установка и результаты проверок

Установка идёт через Termux Rescue (`am start -a com.termux.rescue.INSTALL --es path /sdcard/Download/<apk> --es mode adb`, режим `system` безопаснее по ранним заметкам, но выбран adb по решению владельца). Установка перезапускает Termux; после установки 2026-11-24 телефон перезагрузился (watchdog, см. заметку `termux-update-watchdog-reboot`), Termux поднялся нормально.

Проверено на телефоне после установки APK из `9eb0892`:

- `sha256sum -c SHA256SUMS` для шима: все четыре файла OK;
- glibc `node` с шимом видит `/etc/os-release`, `/usr/bin`, `/tmp`, запускает `/bin/sh`, работает на glibc 2.44;
- вход работает, метки `usr` и `login`: `app_data_file:s0:c62,c257,c512,c768`;
- в `$PREFIX/glibc/god-lib` лежат `libSPIRV-Tools.so` и `libwayland-client.so.0.26.0`.

Версии символов нового `libfhs-glibc.so` (собран Ubuntu-компилятором, glibc 2.39): не выше `GLIBC_2.34`, на телефоне glibc 2.44.

## Не проверено

- Работа композитора после исправления с `libc++_shared.so`: в CI-сборке `5924efcd` библиотека в APK есть (проверка CI зелёная), но на телефон этот APK не ставился.
- Запуск `wlrun`, Chromium, XFCE на новой сборке.
- Раздельный экран из `main`.
- `dsu` и `claude-chrome-host` в работе после обновления скриптов.
- Снимок `snapshot-1795513703.txt` сделан до установки, для оценки новой сборки не годится.

## Предостережения

- APK из CI подписан публичным тестовым ключом Termux (`app/testkey_untrusted.jks`): раздавать такие сборки другим нельзя, подделку обновления с этим ключом может выпустить любой.
- Для публичной раздачи нужен собственный ключ; смена ключа потребует удалить приложение (данные Termux потеряются без копии).
- Каждая установка APK запускает пересчёт меток `installd` (~600 тысяч файлов в данных `com.termux`) и может привести к watchdog-перезагрузке. Не использовать переустановку как цикл отладки.
- `wlchromium` и `xfce-status` теперь поставляются в APK, `build-local.sh` их не копирует; при старте приложение перезапишет ручные копии в `$PREFIX/bin` версиями из репозитория.
- `libfhs-glibc.so` в CI собирается кросс-компилятором Ubuntu, на телефоне — тулчейном Termux glibc; разные сборки одних и тех же исходников.

## Влияет ли компилятор на скорость шима (замер 2026-11-24)

Микробенчмарк (glibc-программа, 200 тысяч вызовов, лучший из 7 прогонов, один запуск, телефон под нагрузкой): `syscall()` напрямую, который шим не перехватывает, против `stat`/`open`, которые он перехватывает. Измерялся установленный CI-шим (Ubuntu gcc, glibc 2.39).

| Вызов | ns |
|---|---|
| raw `newfstatat` | 2111 |
| `stat()` путь Android (не переписывается) | 2195 (+4%) |
| `stat("/usr/bin/sh")` (переписывается) | 2349 (+11%) |
| `stat("/etc/os-release")` (переписывается) | 2171 (+3%) |
| raw `openat`+`close` | 3935 |
| `open()` путь Android | 4398 (+12%) |
| `open("/usr/bin/sh")` (переписывается) | 5030 (+28%) |

Вывод: шим добавляет от десятков до ~1000 нс на вызов, основное время (2–4 мкс) уходит на сам системный вызов (ядро, seccomp Android, SELinux). Различие в компиляторе (gcc или clang, `-O2`) на фоне этого не заметно. Сравнить CI-шим с собранным на телефоне напрямую не удалось: путь к шиму зашит в `execve`-обёртку, подменить его без перезаписи установленной библиотеки нельзя, а перезаписывать её ради замера не стали. Цифры шумные (один прогон), для выводов о процентах нужны повторы.

Ошибка в замере, на которую стоит обратить внимание: в оболочке уже стоит `LD_PRELOAD` с бионик-шимом, поэтому запуск glibc-программы через `ld-linux-aarch64.so.1 --library-path ...` вручную ломается (`libdl.so: cannot open shared object file`). Glibc-программы нужно запускать напрямую, шим оборачивает `exec` сам; `timeout` ставить до `env`.
