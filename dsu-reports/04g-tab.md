# Отчёт 04g: `dsu --tab` (4г) и доработка `dsuset` (4а, шаг 4) — Sonnet → архитектору

Дата: 2026-11-11.

## 1. Что сделано
- **Доработка `dsuset` по замечанию архитектора**: `/data/data/com.termux/files/home/mods-src/dsuset/java/dsuset/DsuSet.java` — фильтр отправителя заменён с `com.termux.permission.RUN_COMMAND` на `android.permission.WRITE_SECURE_SETTINGS`. Проверено по источникам: в `app/src/main/AndroidManifest.xml` (строки 15–20) `com.termux.permission.RUN_COMMAND` только **объявлено** (`<permission … dangerous>`), `<uses-permission>` на него нет; `gdumpsys package com.termux` не показывает его среди запрошенных/выданных. Пересобрано `modbuild`: `~/.termux/mods/dsuset/classes.dex` обновлён (02:36 → 02:40, 4000 байт), в нём есть строка `WRITE_SECURE_SETTINGS` и нет `RUN_COMMAND`. **Загрузка мода по-прежнему ждёт перезапуска Termux.**
- **4г**: `god/runtime/dsu` → `1.3.0-tab` (установлен). Новая опция `dsu --tab [ОПЦИИ]` = `am startservice -n com.termux/com.termux.app.RunCommandService -a com.termux.RUN_COMMAND` с `RUN_COMMAND_PATH=$PREFIX/bin/dsu`, `…_ARGUMENTS` (через запятую; запятая в аргументе отвергается), `…_WORKDIR=$PWD`, `…_BACKGROUND=false`, `…_SESSION_ACTION=0` (переключиться на новую сессию и открыть Activity). `CLAUDE.md` обновлён.

## 2. Что проверено на устройстве
| Проверка | Результат |
|---|---|
| Приложение стартует сервис интентом от своего uid | `am startservice … RunCommandService` принят (без разрешения: компонент того же приложения; `allow-external-apps=true` включён) |
| Терминальная сессия, `SESSION_ACTION=3` («не открывать») | сессия создаётся, но **процесс не запускается**: скрипт не оставил следов (ни `4g.out`, ни `4g.touch`), ни `bash -c` через `RUN_COMMAND_ARGUMENTS`. Причина (по коду `TerminalSession`): эмулятор/процесс инициализируется при подключении `TerminalView` к сессии, пока вкладка не показана — процесса нет |
| `SESSION_ACTION=0` | скрипт выполнился: `uid=10318`, `tty=/dev/pts/32` |
| Фоновый runner (`BACKGROUND=true`, `app-shell`) | скрипт выполнился без tty (`not a tty`), uid 10318 |
| `dsu --tab` | открыта новая вкладка; процессы `bash …/bin/dsu` и `adb -s 10.14.238.211:36565 shell -t …` существуют (интерактивный `dsu` запущен в вкладке); затем я завершил их по PID (вкладка осталась «Process completed»), тестовые файлы удалены |

## 3. Что не проверено и почему
- Видимое поведение вкладки (приглашение, баннер, размер окна) — не наблюдал экран; подтверждено только наличием процессов `dsu`/`adb shell -t`.
- `dsu --tab` с опциями (`--tx`, `-E`, `-s`) — не запускал.
- Работа мода `dsuset` и `am broadcast`: ждёт перезапуска Termux.

## 4. Отклонения от плана
1. Для 4г принято `SESSION_ACTION=0`: при значениях «не открывать» (2/3) процесс сессии не стартует, пока вкладка не показана (подтверждено опытом).
2. Вместо «одной команды/ярлыка» — опция `dsu --tab`; ярлык на главный экран не делал (нужен отдельный запрос пользователя).

## 5. Риски и находки вне плана
- `dsu --tab` открывает Termux поверх экрана пользователя (как и тестовый запуск с действием 0).
- Для `--tab` аргументы передаются списком через запятую; значения с запятой не поддерживаются.
- Мои тесты `RUN_COMMAND` создали несколько сессий Termux (две с «не открывать» остались без процессов, одна выполнила скрипт) — после перезапуска Termux они исчезнут.

## 6. Предложение следующего шага
Принять 4г и доработку `dsuset`. Для завершения 4а нужен **перезапуск Termux пользователем** (я предупрежу, что он убьёт `socat`/`virgl`/Shizuku-сессии и текущую сессию Claude Code); после него — проверка по плану: `god-mods.log` → `external dsuset ok`; `am broadcast -a dsu.ADB_WIFI --es op get`; `--ei value 0`, пауза, затем **без канала shell** `--ei value 1` → новый `adb-connect-port`, `adb connect` без `pair`; затем шаг 5 (интеграция в `dsu`). 4в — только если пользователь назовёт нужную утилиту.
