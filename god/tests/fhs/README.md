## Супервизор fhs-run и промахи кеша путей (2026-11-12, второй этап)

```
python3 god/tests/fhs/sup.py --baseline /path/to/dir   # каталог с прежними fhs-run.c и fhsmap.h
python3 god/tests/fhs/cache.py --baseline /path/to/previous/fhsmap.h
```

`sup.py` собирает прежний и новый `fhs-run` во временном каталоге и ничего не ставит.
Сначала корректность: `supops.c` выполняет 45 проверок через FHS-имя `/tmp/…`
(создание, запись, stat/statx, access, chmod, utimensat, symlink/readlink, rename
в том числе с относительным именем, link, чтение, строка на границе страниц, строка
без завершающего нуля, слишком длинное имя, неверные указатели, bind/connect AF_UNIX,
удаление). Вывод должен совпасть с `supops.expected` у прежнего супервизора, у нового
и у нового, собранного с `-DFHS_VM_DEFAULT=0` (запасной путь через `/proc/PID/mem`).
`link: Permission denied` в эталоне — это запрет hardlink в Android, а не ошибка.
Без `--baseline` сравнение идёт с `aac2c260`.

Что изменено в `fhs-run.c`:
- память процесса читается и пишется через `process_vm_readv/writev`; раньше на каждый
  перехваченный вызов открывался и закрывался `/proc/PID/mem`. Строка читается кусками
  до границы страницы. При `ENOSYS` или отказе остаётся прежний путь;
- `SECCOMP_USER_NOTIF_FD_SYNC_WAKE_UP` (Linux 6.6+, на телефоне 6.12): супервизор
  будится на том же ядре. Отключается `FHS_SUP_NOSYNC=1`; старое ядро просто откажет.

Что изменено в `fhsmap.h` (только промах кеша): кандидаты строятся по одному прямо
в выходной буфер через `memcpy`, без `snprintf` и без построения путей, которые не
понадобятся. Порядок проверок и обрезка до `PATH_MAX` прежние. `paths.py` теперь
сравнивает 2112 результатов с `aac2c260`: добавлены имена, существующие только в одном
из трёх деревьев, похожие префиксы (`/usr/binx`, `/libx`), `/usr/sbin`, `/lib64`,
`/usr/libexec` и длины около `PATH_MAX`.

Замеры (медианы, чередование запусков; «до» — состояние после первого этапа):

| Нагрузка | До | После | Ускорение |
|---|---:|---:|---:|
| `ls -l /usr/bin` ×5 под супервизором (~14 000 перехватов) | 1,54–1,75 с | 0,83–0,84 с | 1,9–2,1× |
| stat абсолютного неподменяемого пути | 37–60 мкс | 24–30 мкс | 1,2–2,1× |
| stat относительного пути | 36–54 мкс | 22–28 мкс | 1,3–2,0× |
| stat подменяемого пути | 39–57 мкс | 29–37 мкс | 1,1–1,6× |
| openat подменяемого пути | 42–57 мкс | 35–42 мкс | 1,1–1,35× |
| промах кеша, имя существует (без супервизора) | 2,8–3,1 мкс | 2,0–2,1 мкс | 1,4–1,5× |
| промах кеша, имени нет ни в одном дереве | 8,2–11 мкс | 7,0–7,4 мкс | 1,2–1,5× |

Микрозамеры супервизора сильно зависят от частоты и нагрева ядер: разброс между
запусками больше, чем между вариантами в одном запуске, поэтому смотреть нужно на
отношение внутри одного запуска. Нижняя граница на этом телефоне — обмен байтом между
двумя процессами через pipe: 12–14 мкс. Тот же вызов без супервизора стоит 0,6–2 мкс,
то есть перехват остаётся дорогим по природе (два переключения процесса на вызов).

Проверено и отброшено: `newfstatat` вместо `faccessat` для проверки существования
(0,91–0,98×, медленнее). Закрепление на одном ядре время цикла не уменьшает.

Не проверено: установка пакетов через `dapt` с новым супервизором, работа на ядре
старше 6.6, многопоточные программы под супервизором, длительная работа.


## Быстрый путь, учётные файлы, refresh_caches (2026-11-12/13, третий этап)

```
python3 god/tests/fhs/fast.py
python3 god/tests/fhs/refresh.py
```

`fast.py` собирает супервизор, оба шима и `libdapt-nolink.so` из рабочего дерева во временный каталог и запускает программы
как `linker64 fhs-run env LD_PRELOAD=… ПРОГРАММА` (иначе шим вызывающей оболочки подставит установленную копию).
`fastops.c` — 171 строка результатов вызовов libc (stat, access, open, readlink, statx, создание, переименование, права,
время, ссылки, каталоги) по FHS-именам, плюс вызовы, которые libc делает сама сразу после помеченных (fopen, opendir,
realpath). Вывод должен совпасть: только супервизор / быстрый путь / быстрый путь с `FHS_FAST_OFF=1`, в обычном режиме и
с `FHS_DEBIAN=1`; для glibc-шима сравниваются быстрый путь и `FHS_FAST_OFF=1`. Число перехватов берётся из `FHS_SUP_STATS`.
Затем dpkg ставит пакет на 300 файлов во временное дерево: дерево и список файлов совпадают, перехватов меньше вдвое;
пакет с владельцем не из встроенных Android ID не должен давать больше 60 перехватов на файл.

`refresh.py` проверяет `refresh_caches` на временном дереве с подставным `fhs-run`: первый запуск строит всё, без изменений
строится только fc-cache, новый/изменённый/удалённый входной файл и чужая перезапись кеша пересобирают ровно свой кеш,
неудачная сборка повторяется, `force` строит всё.

Результаты 2026-11-13: перехваты 1153 → 514 (bionic), 1069 → 446 (glibc), dpkg 4966 → 1700; владелец не root: 1711
против 74 288 с `FHS_SUP_ACCT=1`. `refresh_caches` на настоящем дереве: 5,5 с → 0,24 с без изменений.

Ошибки, найденные этими тестами: метка, оставшаяся в регистре x5 после `syscall()` libc, пропускала следующий внутренний
вызов libc мимо супервизора (теперь `fhs_tagged()` обнуляет x5); кеш `fhs_fast_active()`, заполненный до появления
`environ`, выключал быстрый путь.


### ABI 2 и O_PATH (2026-11-13)

Метка быстрого пути теперь не значение в регистре x5, а адрес: шим делает свои вызовы из трамплина по фиксированному
адресу, фильтр сравнивает `instruction_pointer`. Причина — `sigops.c`: таймер прерывает цикл `stat()` и в обработчике
вызывает `opendir("/usr/bin")`. С меткой в x5 (даже с обнулением после вызова) 9241 из 9964 обработчиков получили путь
без подмены; с трамплином 0 из 9956. `fast.py` запускает этот тест и требует ноль.

`realpath()` и `fchmodat(AT_SYMLINK_NOFOLLOW)` по подменяемому имени под супервизором раньше возвращали EBADF (ядро не
передаёт O_PATH-дескрипторы через `SECCOMP_IOCTL_NOTIF_ADDFD`); теперь супервизор подставляет обычный дескриптор на
чтение. `fast.py` проверяет оба вызова, `supops.c` — сырое открытие с `O_PATH` (строка `new: O_PATH open`).

## Супервизор fhs-run: параллельность, umask, размеры структур (2026-11-24)
```
python3 god/tests/fhs/supnew.py [--baseline-rev REV] [--only concurrent|umask|statsize|stress]
```
`supnew.py` собирает базовый `fhs-run` (по умолчанию ревизия `45be14f7`) и рабочий в временном каталоге, запускает `supnew.c` под обоими
через `/system/bin/linker64` (обход подмешивания шима при `exec`; программа сама сообщает `shim_loaded`, и тест требует `0`: иначе проверялся
бы шим, а не супервизор) и ничего не устанавливает. Проверки:
- `concurrent`: поток блокирует супервизор в `open()` FIFO, `stat` из другого потока должен вернуться быстрее 1000 мс (базовый ждёт ~2,6 с, пока
  harness не откроет FIFO на запись; без этого реальная программа, у которой писатель тоже под супервизором, зависла бы навсегда);
- `umask`: файл и каталог под `umask(0)`, `077`, `022` получают права по `umask` программы, а не супервизора (harness запускается с `umask 022`);
- `statsize`: за границу `struct stat`/`struct statx` ничего не записывается (защитная область 0xAA), поля совпадают с прямым системным вызовом;
- `stress`: 8 потоков создают, проверяют и удаляют файлы через супервизор одновременно, ошибок и остатков нет.
Базовый супервизор обязан провалить `concurrent` и `umask` (известные дефекты); иначе тест ничего не доказывает, и `supnew.py` падает.

Что изменено в `fhs-run.c` (одна версия, проверено `sup.py`, `fast.py`, `fsops.py`, `paths.py`, `refresh.py`, `supnew.py`):
- размер структуры `stat`, которую ядро записывает в память программы, вычисляется для ABI (`KSTAT_SZ`), а не равен 128; буфер обнуляется;
- супервизор работает с `umask(0)` и сам применяет `umask` программы (строка `Umask:` из `/proc/TID/status`) к режиму `open(O_CREAT)` и `mkdirat`;
- нет `poll()` перед каждым получением уведомления (блокирующий `NOTIF_RECV`);
- один рабочий поток; если он занят одним вызовом дольше 100 мс, наблюдатель добавляет помощников (до `FHS_SUP_THREADS`, по умолчанию 4;
  1 отключает), помощник уходит, когда никто больше не завис. Постоянный пул из 4 потоков был медленнее вдвое: каждое уведомление будило другое,
  остывшее ядро;
- `SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV` (Linux 5.19+), с повтором без флага на `EINVAL`.

Замер (`sup.py`-подобный, медианы 6 запусков с чередованием, мкс на вызов, телефон под нагрузкой, цифры шумные): до `stat_relative` 36, `open_mapped` 80;
после 30 и 50. На 32-битных ABI и x86_64 не запускалось, только собирается (`_Static_assert` на размер буфера).
